# BM25 入门：面向 DevSquad 代码检索

> 读者：软件工程学生熊子健  
> 实践目标：在 DevSquad 项目中亲手实现 `backend/devsquad/retrieval/bm25.py`，支持按函数或文件切分代码，并对标识符拆词后检索。  
> 本文只讲原理、设计思路和伪代码，不给出可直接提交的完整实现。

## 1. BM25 解决什么问题

### 1.1 从查询到有序结果

给定一个查询和一批文档，检索系统不仅要找出“包含查询词”的文档，还要回答：**哪些文档更相关，应该排在前面？**

BM25（Best Matching 25）就是一种词法相关性排序方法。它综合考虑：

- 查询词在整个语料中是否稀有；
- 查询词在当前文档中出现了多少次；
- 当前文档相对平均文档有多长；
- 同一词重复出现时，边际贡献应逐渐减小。

在 DevSquad 中，一个“文档”可以是一个函数，也可以是一个文件。用户输入 `parseHTTPResponse` 后，系统可以使用 BM25 对候选函数或文件打分，再返回 top-k 及其路径、函数名、行号等元数据。

BM25 本质上是**词袋模型**：它看重词项匹配，但通常不理解词序、语法结构或深层语义。因此，`parse json` 能很好匹配包含这些词的代码，却不会仅凭语义自动匹配一个只包含 `decode` 和 `payload` 的实现。

### 1.2 与 TF-IDF 的区别

TF-IDF 与 BM25 都利用“词频”和“逆文档频率”，但 BM25 对词频和文档长度的处理更有针对性。

| 维度 | 常见 TF-IDF 做法 | BM25 |
| --- | --- | --- |
| 词频 | 常使用原始 `tf`、对数 `tf` 等，再乘 IDF | 使用带饱和的词频因子，重复词的贡献逐渐减小 |
| 文档长度 | 常见实现通过 L2/cosine 向量归一化间接处理 | 用 `b` 和 `avgdl` 显式控制长度归一化 |
| IDF | 常见形式如 `ln(N / df)`，具体实现很多 | 来自概率相关性框架，本文使用带平滑的非负变体 |
| 可调参数 | 取决于具体 TF-IDF 变体 | 主要有 `k1` 和 `b` |
| 最终得分 | 常计算归一化向量的点积或余弦相似度 | 各查询词贡献直接求和，不是余弦相似度，也不是概率 |

不能简单说“BM25 总是优于 TF-IDF”。二者都有多种实现，实际效果取决于语料、分词、参数和评测集。BM25 的主要优势是：**用较少且可解释的机制，同时处理稀有词、重复词和文档长度。**

## 2. 公式逐项讲解与手算示例

### 2.1 本文采用的公式

对查询 `Q` 和文档 `D`，本文把每个不同查询词的贡献相加：

\[
\operatorname{score}(D,Q)
= \sum_{t \in Q}
\operatorname{IDF}(t)
\cdot
\frac{f(t,D)(k_1+1)}
{f(t,D)+k_1\left(1-b+b\frac{|D|}{\operatorname{avgdl}}\right)}
\]

本文采用常见的非负 IDF 变体：

\[
\operatorname{IDF}(t)
= \ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right)
\]

符号含义如下：

| 符号 | 含义 |
| --- | --- |
| `N` | 语料中的文档总数 |
| `df(t)` | 包含词 `t` 的文档数；同一文档中出现多次仍只计 1 |
| `f(t,D)` | 词 `t` 在文档 `D` 中的词频，即 TF |
| `|D|` | 文档 `D` 的**分词后 token 数** |
| `avgdl` | 所有文档的平均长度，即 `sum(|D|) / N` |
| `k1` | 控制词频饱和速度，常用起点约为 `1.2 ~ 2.0` |
| `b` | 控制长度归一化强度，常用起点为 `0.75` |

注意：经典资料也常把 IDF 写成 `ln((N-df+0.5)/(df+0.5))`，不加外面的 `1+`。两种形式的数值和边界行为不同。实现、手算、单测以及与第三方库对拍时，必须先确认使用的是哪一种。本文所有计算都统一使用上面的**非负变体**。

### 2.2 IDF：稀有词更有区分度

`df(t)` 越小，说明包含词 `t` 的文档越少，IDF 通常越大。例如，某个项目独有的类名往往比 `return` 更能区分文档。

`df` 是文档频率，不是总出现次数。假设一个词在同一个函数中出现了 20 次，但其他文档都没有出现，那么它的 `df` 仍然是 1，而它在该函数中的 `f` 是 20。

本文的非负 IDF 变体不会让高频词贡献变成负数。即使词出现在所有文档中，由于平滑项的存在，其 IDF 也通常是一个接近 0 的正数，而不是恰好等于 0。

### 2.3 词频饱和与 `k1`

先暂时把长度相关部分记为：

\[
K_D=k_1\left(1-b+b\frac{|D|}{\operatorname{avgdl}}\right)
\]

词频因子就可以写成：

\[
r(f,D)=\frac{f(k_1+1)}{f+K_D}
\]

当 `K_D` 固定时：

- `f` 越大，得分越高，但增长会越来越慢；
- 当 `f` 趋向很大时，`r(f,D)` 趋近 `k1+1`，不会无限线性增长；
- `k1` 越小，饱和越早；`k1` 越大，词频作用越接近线性增长。

这符合一个直观判断：一个函数第一次出现 `tokenizer`，能提供较强的匹配证据；从第 20 次增加到第 21 次，新增证据通常很有限。

### 2.4 长度归一化与 `b`

长文档天然包含更多词，更可能“碰巧”命中查询，也可能只是内容冗长。长度归一化通过 `|D| / avgdl` 调整词频因子：

- `b = 0`：不做长度归一化；
- `b = 1`：使用完整的相对长度归一化；
- `0 < b < 1`：在两者之间折中；
- 文档恰好等于平均长度时，`|D|/avgdl = 1`，所以 `K_D = k1`。

这不是在说“长文档质量差”，而是在校正文档长度带来的匹配机会差异。`k1 = 1.2 ~ 2.0`、`b = 0.75` 是常用起点，不是所有代码语料上的最优答案；应在独立验证集上调参，而不是根据测试集结果反复调参。

### 2.5 三个小文档的完整手算

下面是为了验算公式而**人为构造的微型语料**，不是 DevSquad 的真实代码或实验结果。假定已经完成小写化和拆词，token 序列如下：

| 文档 | token 序列 | 长度 `|D|` | `f(bm25,D)` | `f(search,D)` |
| --- | --- | ---: | ---: | ---: |
| `D1` | `bm25 bm25 bm25 search code code` | 6 | 3 | 1 |
| `D2` | `bm25 search` | 2 | 1 | 1 |
| `D3` | `bm25 code code code` | 4 | 1 | 0 |

查询为：

```text
bm25 search
```

参数取：

```text
k1 = 1.2
b  = 0.75
```

#### 第一步：计算 `N`、`df` 和 `avgdl`

共有 3 个文档，所以 `N = 3`。

- `bm25` 出现在 `D1、D2、D3`，所以 `df(bm25) = 3`；
- `search` 出现在 `D1、D2`，所以 `df(search) = 2`。

平均文档长度为：

\[
avgdl = \frac{6+2+4}{3}=4
\]

#### 第二步：计算两个查询词的 IDF

对 `bm25`：

\[
\begin{aligned}
IDF(bm25)
&=\ln\left(1+\frac{3-3+0.5}{3+0.5}\right)\\
&=\ln\left(\frac{8}{7}\right)\\
&\approx 0.1335313926
\end{aligned}
\]

对 `search`：

\[
\begin{aligned}
IDF(search)
&=\ln\left(1+\frac{3-2+0.5}{2+0.5}\right)\\
&=\ln(1.6)\\
&\approx 0.4700036292
\end{aligned}
\]

`bm25` 出现在更多文档中，因此 IDF 明显更低。

#### 第三步：计算每篇文档的长度因子 `K_D`

对 `D1`，`|D1|/avgdl = 6/4 = 1.5`：

\[
K_{D1}=1.2(1-0.75+0.75\times1.5)=1.65
\]

对 `D2`，`|D2|/avgdl = 2/4 = 0.5`：

\[
K_{D2}=1.2(1-0.75+0.75\times0.5)=0.75
\]

对 `D3`，`|D3|/avgdl = 4/4 = 1`：

\[
K_{D3}=1.2(1-0.75+0.75\times1)=1.2
\]

#### 第四步：计算词频因子

`D1` 中，`bm25` 出现 3 次：

\[
r_{D1,bm25}
=\frac{3(1.2+1)}{3+1.65}
=\frac{6.6}{4.65}
\approx1.4193548387
\]

`D1` 中，`search` 出现 1 次：

\[
r_{D1,search}
=\frac{1(1.2+1)}{1+1.65}
=\frac{2.2}{2.65}
\approx0.8301886792
\]

`D2` 中两个查询词都只出现 1 次，长度因子也相同，所以二者的词频因子均为：

\[
r_{D2,bm25}=r_{D2,search}
=\frac{2.2}{1+0.75}
\approx1.2571428571
\]

`D3` 中只有 `bm25` 命中：

\[
r_{D3,bm25}=\frac{2.2}{1+1.2}=1
\]

`D3` 的 `search` 词频为 0，贡献为 0。

#### 第五步：乘 IDF 并求和

对 `D1`：

\[
\begin{aligned}
score(D1,Q)
&=0.1335313926\times1.4193548387
 +0.4700036292\times0.8301886792\\
&\approx0.1895284282+0.3901916922\\
&\approx\mathbf{0.5797201204}
\end{aligned}
\]

对 `D2`：

\[
\begin{aligned}
score(D2,Q)
&=(0.1335313926+0.4700036292)\times1.2571428571\\
&\approx\mathbf{0.7587297418}
\end{aligned}
\]

对 `D3`：

\[
score(D3,Q)=0.1335313926\times1
\approx\mathbf{0.1335313926}
\]

汇总如下：

| 排名 | 文档 | `bm25` 贡献 | `search` 贡献 | 总分 |
| ---: | --- | ---: | ---: | ---: |
| 1 | `D2` | 0.1678680364 | 0.5908617053 | **0.7587297418** |
| 2 | `D1` | 0.1895284282 | 0.3901916922 | **0.5797201204** |
| 3 | `D3` | 0.1335313926 | 0 | **0.1335313926** |

这个例子同时说明：

1. **稀有词贡献更大**：同一文档中，`search` 的 IDF 高于 `bm25`。
2. **重复词不会线性加分**：`D1` 中 `bm25` 出现 3 次，但其总得分并没有变成只出现 1 次时的 3 倍。
3. **长度会影响结果**：`D1` 虽然包含更多 `bm25`，但文档较长，两个词的词频因子都受到长度归一化影响；最终短文档 `D2` 排名第一。
4. **不能只看命中次数**：`D3` 也命中了 `bm25`，但缺少 IDF 更高的 `search`，所以得分最低。

若想单独观察“饱和”而不混入长度差异，可固定 `K_D = 1.2`：当词频从 1 增加到 3 时，词频因子从 `2.2/(1+1.2)=1` 变为 `6.6/(3+1.2)≈1.5714285714`，而不是变成 3。

## 3. 代码检索场景的特殊处理

### 3.1 先确定“文档”的粒度

同一份源码可以建立不同粒度的索引：

| 粒度 | 优点 | 需要注意的问题 |
| --- | --- | --- |
| 函数/方法 | 返回位置精确，上下文较集中，适合直接交给后续代码生成流程 | 过短函数的统计量不稳定；函数签名、注释是否计入要明确 |
| 文件 | 保留跨函数上下文，切分实现简单 | 长文件噪声更多，命中位置不够精确，长度归一化影响更明显 |

建议每次索引保持同一粒度，分别计算函数语料和文件语料的 `avgdl`。不要把大量短函数和少量长文件混在同一语料中，再共用一个平均长度。

每个 chunk 至少应保留能定位源码的元数据，例如：

- `doc_id`；
- 文件路径；
- chunk 类型（函数或文件）；
- 函数/方法名（如果存在）；
- 起止行号；
- 编程语言。

BM25 负责排序，元数据负责把排序结果还原成用户可用的代码位置。

### 3.2 驼峰与下划线拆词

代码查询经常要求“局部词”也能命中。例如，查询 `http server` 应该有机会匹配 `HTTPServer`。

一个明确的拆词流程可以是：

1. 先按下划线等非字母数字边界切段；
2. 再识别小写到大写、缩写词到后续单词等驼峰边界；
3. 正确处理连续大写缩写，避免把 `HTTP` 拆成 `H、T、T、P`；
4. 统一转为小写；
5. 对索引文本和查询文本执行完全相同的规则。

例如：

```text
原始标识符：parseHTTPResponse_v2
拆分结果：  parse、http、response、v2
```

`HTTPServer` 应优先拆成 `http、server`，而不是逐个大写字母拆分。`v2`、`sha256` 等 token 通常有检索价值，不应仅因为包含数字就删除。

还可以同时保留“完整标识符 token”和“拆出的子词 token”，兼顾精确匹配与局部匹配。但这会改变 `df`、词频和文档长度，必须明确是否去重、如何计数，不能无意中对同一文本重复加权。

### 3.3 大小写

代码检索通常先做大小写折叠，例如统一转为小写，减少 `ParseJSON`、`parseJson` 等写法带来的大小写差异；配合驼峰拆词后，查询 `parse json` 也能匹配它们。如果还希望查询 `parsejson` 命中，可以按上一节的建议额外保留完整标识符的规范化 token。

但原始源码仍应完整保留，用于结果展示、精确匹配和后续处理。规范化 token 用于建索引，不等于修改源代码。若将来同时保留大小写敏感特征，也应把它作为独立设计，而不是让索引和查询使用不同的大小写规则。

### 3.4 停用词

自然语言检索常删除 `the、a、of` 等停用词，但代码检索不能照搬一份激进词表：

- `async、await、return、lambda` 等语言关键字本身可能就是查询目标；
- `self、this` 很频繁，但在某些对象或方法检索中仍有意义；
- 单字母可能是噪声，也可能是语言名、变量名或用户明确查询的符号；
- BM25 的 IDF 本身就会降低普遍词项的权重。

因此，初版宜采用**保守、可测试的规则**。如果确实要删除停用词，必须让索引与查询使用同一张表，并通过有标注的代码查询评估收益和损失。

### 3.5 为什么与向量检索互补

| 检索方式 | 更擅长的情况 | 典型短板 |
| --- | --- | --- |
| BM25 | 精确或近似的标识符、API 名、错误码、稀有术语；结果容易解释 | 同义表达、跨语言表达和“意思相近但词不同”的匹配较弱 |
| 向量检索 | 自然语言意图、同义改写、语义相近但字面不同的代码 | 对稀有标识符的精确区分未必稳定，结果解释较困难 |

例如，查询 `HTTPConnectionError` 时，精确 token 很重要；查询“如何把这个数据解码成对象”时，目标代码可能只包含 `parse` 和 `decode`，语义匹配更重要。

混合检索可以使用加权融合，也可以使用 RRF（Reciprocal Rank Fusion，倒数排名融合）等按排名融合的方法。**不要直接相加原始 BM25 分数和向量相似度**：两者的量纲和分布不同。若使用加权分数，需要先明确归一化方法；若想减少分数尺度带来的问题，可以优先考虑排名融合。

## 4. 实现思路与伪代码

### 4.1 建议的数据结构

索引阶段需要保存：

- `postings`：倒排索引，`term -> [(doc_id, tf), ...]`；
- `df`：`term -> 包含该词的文档数`，也可由 posting list 长度得到；
- `doc_len`：`doc_id -> token 数`；
- `N`：文档总数；
- `avgdl`：平均文档长度；
- `idf`：预计算后的词项权重；
- `K[doc_id]`：预计算的长度因子；
- `metadata`：`doc_id -> 路径、函数名、行号等定位信息`。

倒排索引的意义是：查询时只访问至少包含一个查询词的文档，而不是扫描整个语料。

### 4.2 建索引、计算 `df` 与 `avgdl`

以下是结构伪代码，不是某一门语言的完整实现：

```text
build_index(documents, k1, b):
    postings = 空的“词 -> posting list”映射
    doc_len  = 空的“文档 ID -> 长度”映射
    N = documents 的数量

    for doc in documents:
        tokens = tokenize_and_normalize(doc.text)
        doc_len[doc.id] = tokens 的数量
        term_counts = 统计 tokens 中每个不同词的出现次数

        for (term, tf) in term_counts:
            把 (doc.id, tf) 加入 postings[term]

    如果 N 为 0，按空索引处理，不能除以 0
    avgdl = 所有 doc_len 之和 / N
    如果 avgdl 为 0（所有文档都没有 token），按空索引处理

    for term in postings:
        df[term] = postings[term] 中不同 doc_id 的数量
        idf[term] = ln(1 + (N - df[term] + 0.5) / (df[term] + 0.5))

    for doc in documents:
        K[doc.id] = k1 * (1 - b + b * doc_len[doc.id] / avgdl)

    返回 postings、df、idf、doc_len、avgdl、K、metadata 等索引数据
```

关键点：

- `term_counts` 的键数决定一个文档为多少个词贡献 `df`，同一文档中的重复词不能重复增加 `df`；
- `doc_len` 必须使用规范化、拆词后的 token 数，而不是字符数、字节数或源码行数；
- `avgdl` 和 IDF 应在整个语料统计完成后确定；
- 函数索引和文件索引若分开建立，各自拥有自己的 `N`、 posting list、`avgdl` 和 IDF。

### 4.3 查询打分

```text
search(query, top_k, index):
    query_terms = tokenize_and_normalize(query) 的不同词集合

    如果 query_terms 为空或 top_k 不大于 0:
        返回空结果

    scores = 空的“doc_id -> 分数”映射，默认值为 0

    for term in query_terms:
        如果 term 不在 index.postings 中:
            继续处理下一个词

        for (doc_id, tf) in index.postings[term]:
            term_factor = tf * (k1 + 1) / (tf + index.K[doc_id])
            scores[doc_id] += index.idf[term] * term_factor

    candidates = scores 中的所有候选文档
    ranked = 按“分数降序、doc_id 升序”排列 candidates
    返回 ranked 的前 top_k 个，并附带对应 metadata
```

这里把查询视为不同词项的集合，重复输入同一个查询词不会额外加权。如果产品需要查询词频权重，可以显式引入 `qtf`，但要同时修改公式说明和测试，不能一边遍历重复词、一边又误以为只计算了一次。

预计算 `K[doc_id]` 可以避免在每个 posting 上重复计算长度归一化。它不改变公式，只是减少重复工作。

### 4.4 取 top-k

候选数为 `C` 时：

- 直接对候选完整排序，易于实现，排序部分通常为 `O(C log C)`；
- 候选很多而 `k` 较小时，可用大小为 `k` 的最小堆，把选择部分降为 `O(C log k)`；
- 无论采用哪种方式，都应规定同分时的次序，例如按 `doc_id` 升序，保证结果可复现。

第一版可以先用简单、正确的方式实现，再通过真实 profiling 判断是否需要堆优化。

### 4.5 最小验证清单

实现后至少验证：

- 用本文三文档算例对拍总分：`D2 > D1 > D3`，并检查接近表中的数值；
- 同一词在单文档重复出现，`df` 仍只增加 1；
- 平均长度文档满足 `K_D = k1`；
- 查询词不在文档中时，该词贡献为 0；
- `parseHTTPResponse_v2` 与查询 `http response` 能按设计命中；
- 索引和查询经过同一个 tokenizer；
- 空语料、空文档、空查询、未知词和 `top_k <= 0` 不产生异常除零或伪结果；
- 同分结果的顺序稳定；
- 函数与文件粒度没有误用彼此的 `avgdl`。

浮点断言应使用合理容差，不要要求十进制展开后的每一位都完全相同。

## 5. 常见坑

1. **把 `df` 当成总词频**  
   `df` 统计“多少文档包含该词”，不是“该词总共出现多少次”。这会让 IDF 全错。

2. **索引与查询分词不一致**  
   索引把 `HTTPServer` 拆成 `http、server`，查询却保留 `httpserver`，会导致本应命中的结果消失。应复用同一个规范化入口。

3. **文档长度口径不一致**  
   `doc_len` 用 token 数，就不能再拿字符数或行数计算 `avgdl`。保留完整标识符又加入子词时，也要统一长度统计口径。

4. **公式括号或参数位置写错**  
   长度项是 `k1 * (1 - b + b * |D| / avgdl)`；分子是 `tf * (k1 + 1)`。建议把 `K_D` 单独计算，并用固定手算例做回归测试。

5. **混用不同 IDF 变体**  
   不加 `1+` 的经典形式可能对出现在超过一半文档中的词给出负 IDF；本文形式保持非负。与库或其他实现对拍时，分差可能来自公式变体，而不是排序代码错误。

6. **拆词导致意外重复计数**  
   同时加入原标识符、 lowercase 形式和所有子词，可能让一个短标识符被人为放大。应明确去重和计数策略，并检查 `doc_len、tf、df` 的变化。

7. **过度删除代码“停用词”**  
   删除 `return、async、self` 或所有单字母 token，可能直接破坏用户查询。普遍词可以先交给 IDF 降权。

8. **增量更新后仍使用旧统计量**  
   增删文档会改变 `N、df、avgdl`，进而影响 IDF 和所有文档的 `K_D`。若第一版不做完整的增量维护，重建索引通常比留下过期统计量更安全。

9. **忽略空输入和确定性**  
   空语料会导致 `avgdl` 除零；只按浮点分数排序而没有同分规则，可能让结果顺序不稳定。

10. **直接融合异质原始分数，或跨查询比较 BM25 分数**  
    BM25 分数随查询词、IDF 和候选集合变化，不是概率。不同查询的原始总分通常不能直接比较，也不能不经处理就和向量相似度相加。

## 6. 五道面试题与参考答案

### 题 1：BM25 为什么需要词频饱和？`k1` 起什么作用？

**参考答案：** 同一个词重复出现提供的相关性证据通常有边际递减效应。如果得分与原始 TF 完全线性，长文档或重复堆砌某个词的文档会被过度奖励。BM25 的词频因子为 `tf * (k1 + 1) / (tf + K_D)`，在固定长度条件下，随着 `tf` 增大，它逐渐趋近 `k1 + 1`。

当 `k1` 趋近 0 且 `tf > 0` 时，词频因子趋近 1，更接近“是否出现”的二元判断；较大的 `k1` 会推迟饱和，使词频作用更接近线性。`k1` 应结合语料验证，而不是机械固定为某个默认值。

### 题 2：`b = 0` 和 `b = 1` 分别意味着什么？为什么不能简单认为长文档更不相关？

**参考答案：** `b = 0` 时，长度归一化项中的 `b * |D| / avgdl` 消失，不再根据文档长度调整词频因子；`b = 1` 时使用完整的相对长度归一化；中间值表示折中。

长度归一化不是对长文档的质量评价，而是校正长文档拥有更多 token、更容易随机命中的统计效应。有些长文档确实更全面、更相关，所以 `b` 是可调参数，不应被解释为“越长越差”的固定规则。

### 题 3：为什么有些 BM25 实现会出现负 IDF？本文的写法如何避免？

**参考答案：** 经典形式 `ln((N-df+0.5)/(df+0.5))` 中，当 `df > N/2` 时，对数内的比值小于 1，因此 IDF 为负。这会让一个常见查询词降低包含它的文档得分，与许多工程系统希望的单调匹配行为不一致。

本文使用 `ln(1 + (N-df+0.5)/(df+0.5))`。由于 `df <= N` 且平滑项为正，对数内始终大于 1，因此 IDF 保持为正。比较实现时必须先核对公式，不能只比较函数名。

### 题 4：倒排索引上的一次 BM25 查询，大致时间复杂度是多少？

**参考答案：** 设查询去重后有 `q` 个词，这些词的 posting list 总长度为 `P`，至少命中一个查询词的候选文档数为 `C`。建索引通常需要线性扫描全部 token；查询打分只遍历相关 posting list，平均为 `O(P)`，而不是扫描全部 `N` 个文档。

如果完整排序，候选选择部分为 `O(C log C)`；如果使用大小为 `k` 的堆，可降为 `O(C log k)`。这里通常假定哈希表查询和更新为均摊常数时间，且 IDF、文档长度和长度因子已经预计算。

### 题 5：你会怎样为代码助手设计 BM25 与向量检索的混合方案？

**参考答案：** 先按函数或文件建立粒度一致的 chunk，保留路径、符号名和行号。BM25 管线对标识符做下划线、驼峰和缩写感知拆词，统一小写化，并保证索引与查询同规则；向量管线为相同 chunk 建立嵌入。

查询时分别取得两路候选，再根据可解释的标识符匹配需求与语义匹配需求进行融合。可以使用归一化后的加权分数，也可以使用 RRF 等排名融合，但不能直接相加量纲不同的原始分数。最后通过有标注的代码查询分别评估单路与混合结果，并检查精确标识符、自然语言意图、无结果查询和定位准确性。
